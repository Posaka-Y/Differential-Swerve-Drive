# アーキテクチャ決定事項

## 確定事項

| 論点 | 決定 |
|---|---|
| LiPo x2 | 6S LiPo x2を並列運用する |
| E-stop | C620系の24V主電源を遮断し、制御系は生かす |
| E-stop個数・表示 | **非常停止ボタンを2個設け、両方のNC安全接点をコンタクタコイルループへ直列接続する(2026-07-19)。** 各ボタンの24V内蔵LEDはTeensyを介さず、E-stop後も生きる`24V_CTRL`からハードワイヤ給電する。点灯条件は操作パネル設計時に確定する |
| E-stop中央接続 | **中央基板に専用`ESTOP_CTRL`ポートを1個設ける(2026-07-25)。** 2個のE-stopを接続する操作パネル側ハーネスを1コネクタへ集約し、ハード直列NCループの往復、独立保護した24V LED電源/GND、各ボタンの補助接点リターンを収容する。コネクタを抜くとNCループが開いてコンタクタが解放されるfail-safe構成とする |
| コンタクタ励磁 | **コンタクタコイルのMOSFET励磁回路をTeensy中央基板へ組み込み、Teensyは励磁許可だけを担う(2026-07-19)。** 2個のE-stop NC接点によるハード遮断を主経路とし、Teensy未起動時はOFFとする |
| 遠隔モータ電源遮断 | **Teensyが`MOTOR_PWR_EN`を落としてコンタクタを解放する遠隔停止に対応する(2026-07-19)。** 停止はラッチし、明示的な再アームまで再励磁しない。mini PC/一般無線経由は補助停止として扱い、正式な安全無線E-stopが必要な場合は認証受信機の接点をNC安全ループへ追加する |
| メインコンタクタ | **所有品のKILIGEN `E228`(24V DC、100A表記)を採用する(2026-07-26)。主回路をMOSFET式solid-state遮断器へ置換せず、機械式コンタクタを継続する(2026-08-06再確認)。** コイル仕様(24V DC、1.8W、300Ω、動作14〜16V/解放6〜8V/最大印加28V DC、コイル電流約75〜80mA)は確認済みでコイルドライバ設計に使用可。正式なDC負荷遮断定格データシートは無いが、**この個体で前回ロボコン機体において約2000W(24V換算で約83A)の通電中にE-stop等で遮断できた実績を確認済み**(2026-07-26)。この実績値を正式定格の代替根拠として扱い、今回の想定最大電流が83Aを明確に超えないことを設計時に確認する。再利用前に主接点の摩耗・ピッティングを目視検査する。MOSFETはコイル駆動、precharge、回生brake chopperへ使用し、主遮断機能を担わせない |
| 機体状態LED | ミッション達成、状態、バッテリー残量を示すテープLED/表示LEDを追加する(2026-07-19)。安全表示は演出LEDから独立させ、LED方式・電圧・電力は部品選定時に確定する |
| LEDテープ制御 | **LEDテープは独立CANノード基板で制御する(2026-07-25)。** 中央TeensyからLEDのDATA線やピクセル列を直接配線せず、拡張CANでモード、色、明るさ、速度、状態などの高位コマンドを送る。LEDノードがアニメーションとピクセル波形をローカル生成し、CANへ毎フレームの全RGBデータを流さない。LED電力は中央PCBを通さず、24V分電点から専用ヒューズ経由で供給する。LEDノードに`STM32G474RET6`は使用せず、ネイティブCANを持つSTM32G0B1クラスの小型MCUを使用する |
| GUI | mini PCで動かす |
| mini PC機種 | **GMKtec NucBox G2を採用する(2026-07-19)。** 24V常時通電制御系から12V DC-DCで給電し、E-stop後もGUI・ログ・診断を継続できる構成とする |
| Motor Enable判定 | Teensy側で行う |
| キャリブレーション保存 | 各差動ステアユニットに保存する。**方式はMCU Flashに保存するソフトウェアオフセット**(AMT22内蔵のSet Zero Pointは使わない: 書込ごとにエンコーダNVMを消費し、静止+リセットが必要で、定期再ゼロ点調整の運用と相性が悪い。G4はEEPROM無しのためFlashページのエミュレーションで実装し、CRC付きで保存する) |
| ノード外部接続 | **電源とCANを分離する(2026-07-17)。** 電源は中央基板から各ノードへ5V/GNDをスター分配し、CANはCOMM_A/COMM_B/GNDをバスごとにデイジーチェーン接続する。従来の4線一体ハーネス案はCANがスター状になりやすいため不採用 |

| 目標値FF配信 | **SET_TARGET_FF(0x110+id、ステア角速度FF+ホイール加速度FF)を中央CANへ追加(2026-07-06)。** 目標ステア角は連続unwrap角(±180°で折り返さない)。FF未受信時はFF=0で従来動作(後方互換) |
| 駆動目標の加減速・停止 | **中央Teensyは`ωw`をステップ送信せず、加速・減速を別レートにしたランプを通す(2026-07-31)。** 高rpmからの急減速・直接の正逆反転は回生によるDCバス電圧上昇と電源保護停止を招くため禁止し、反転は必ず0rpmを経由する。通常STOPは`現在rpm/減速率+余裕時間`だけ閉ループ減速してからdisableする。E-stop/緊急Disableは安全を優先し、この通常停止シーケンスの例外とする |
| ステア目標の加速・制動 | **中央のステアプロファイルは加速率と制動率を別パラメータにする(2026-07-31)。** 最大速度へ早く到達する加速率と、局所追従遅れを見込んで減速開始を決める制動率を分離する。単一ユニット空走初期値は最大240deg/s、加速3600deg/s^2、制動2250deg/s^2。3輪実装では中央が同一時刻断面を生成し、ユニットが独自に軌道形状を変更しない責務分担を維持する |
| 到着時間と収束完了 | **中央の通常軌道は10% motor-rpm予備を持つplanned包絡線で最短時間を計算し、初期time scaleを2.0とする(2026-07-31)。** 3輪を個別時間で動かさず、最遅モジュールに全体を同期する。軌道時間と追従収束は分離し、各ユニットはSTATUS3の`MOTION_SETTLED`(角度・実steer rpm・wheel追従・steer/wheel FF停止を100ms継続)を返す。中央は全輪フラグと自分のプロファイル完了を確認して到着確定する。空走初期の監視余裕は軌道終了後0.35sで、接地後のp99実測に更新する。期限超過時は制約を破って指令を強めず、ETA延長・全体減速・必要時停止とする |
| 負荷適応制御の発展順序 | **現行mode PIを土台に、FF強化→摩擦補償→mode-space DOB→状態推定→必要時MPCの順で進める(2026-07-09)。** G474は1kHz局所ロバスト制御(PI+FF+DOB)と安全ガードに集中し、3輪協調・制約最適化・MPC候補はTeensy/mini PC側へ置く。詳細は `docs/control/LOAD_ADAPTIVE_CONTROL_ROADMAP.md` |

## 差動ステアユニットの抽象化

中央制御から見た差動ステアユニットは、C620やM3508を直接操作する対象ではなく、以下のような高レベルのCANノードとして扱う。

中央からユニットへ送るもの:

- 目標ホイール回転数
- 目標ステア角度
- 有効/無効指令
- キャリブレーション指令

ユニットから中央へ返すもの:

- 現在ホイール回転数
- 現在ステア角度
- モーター状態
- AMT22状態
- エラー状態
- キャリブレーション状態

ユニット内部では、NUCLEO-G474REがAMT22の絶対角とC620のフィードバックを統合し、2個のM3508へ差動指令を出す。

## 通信構成の決定

**2026-07-02にG474のFDCAN複数系統を根拠として中央通信をCANへ確定し、下記A案(RS485)を不採用とした。2026-07-06に主試験機をCAN 2系統のMatek CAN-G474へ変更したが、採用構成「2バスCAN」と最終G474RET6自作基板は変更しない。**

目標は、中央から各ユニットへ `VIN_CONTROL / GND_CTRL / COMM_A / COMM_B` の4線だけを通し、C620の存在をユニット内に隠すこと。この抽象化は物理層がCANになっても変えない。

```text
中央駆動通信 (G474 FDCAN1、CAN FD nominal 1Mbps/data 2Mbps):
  Teensy <--> 各ユニットMCU     COMM_A/B = 中央CAN_H/L

ユニット内CAN (FDCAN2想定、1Mbps固定):
  ユニットMCU <--> C620 #1
              <--> C620 #2

センサー通信 (Teensy CAN1、Classic CAN 1Mbps):
  Teensy <--> F405オドメトリ/IMU
```

中央CANにはC620の生IDやフィードバックを流さない。中央からはユニット単位の抽象化されたメッセージだけを見る。ユニットMCUはトランシーバを2個持つ(中央用+C620用)。

## 候補構成(検討記録。結論は上記の通り2バスCAN)

### 採用案: 2バスCAN構成

```text
Teensy
  |
  | 中央CAN (COMM_A/B)
  v
ユニットMCU (G474RE, FDCAN x2使用)
  |
  | C620専用CAN
  v
C620 x2
```

利点:

- A案と同じくC620を中央から完全に隠せる。
- RS485のような独自フレーム設計・CRC・半二重の送受切替が不要。CANのアービトレーション・CRC・ACKをそのまま使える。
- Teensy 4.xのFlexCANと直接つながる。
- ユニット側ファームはFDCANドライバ1本で中央・C620の両方を扱える。

成立条件:

- ユニットMCUにFDCANが2系統必要。**G474REはFDCAN 3系統なので成立**(G431KBは1系統で不成立。これがボード確定の決め手)。
- キャリアにCANトランシーバが2個必要。

### A案(不採用): RS485 + 内部CAN構成

```text
Teensy
  |
  | RS485 4線
  v
ユニットMCU
  |
  | ユニット内CAN
  v
C620 x2
```

利点:

- 中央からC620を完全に隠せる。
- ユニットが本当に自己完結モジュールになる。
- ユニットMCUのCANをC620専用にできる。
- NUCLEO-G431KBのCANが1系統でも成立しやすい。

課題:

- RS485用のパケット設計とCRCが必要。
- 中央主導のポーリング方式にする必要がある。

### B案: 1 CAN共有構成

```text
Teensy
  |
  | CAN共有バス
  |-- ユニットMCU x3
  |-- C620 x6
```

利点:

- ハードウェアが単純。
- NUCLEO-G431KBのCAN 1系統でも成立しやすい。

課題:

- 中央CANにC620の生IDが流れる。
- ユニット抽象化はソフト上の約束になる。
- CAN帯域とID設計をより厳密に管理する必要がある。

### C案: 外付けCAN追加

```text
中央CAN: STM32内蔵FDCAN
C620 CAN: 外付けCANコントローラ + トランシーバ
```

利点:

- NUCLEO-G431KBを使いつつ、2 CAN構成に近づけられる。

課題:

- 部品が増える。
- 手ハンダ性、ファーム実装、基板面積が悪化する。

## 現時点の結論(2026-07-02)

G474のFDCAN複数系統を使用して2バスCAN構成を採用する。主試験機はMatek CAN-G474、NUCLEO-G474REは予備とする。A案(RS485)はG431KB前提の検討記録として残す。

外部コネクタのシルクは従来方針通り `CAN_H/L` ではなく `COMM_A/B` とする。物理層がCANでも抽象名を保つことで、将来の変更に外部仕様名を保てる。
