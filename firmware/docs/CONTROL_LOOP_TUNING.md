# Differential control-loop tuning notes

最終更新: 2026-07-06(RoboMaster系オープン実装と比較し、積分独立クランプ等を導入)

## 目的

入力を「目標ホイールrpm」と「目標ステア角」とし、AMT222A-Vの絶対角およびC620 x2の
rpmフィードバックから、C620電流指令を生成する。

## 現在の制御構成(確定)

```
角度P(deadband付き) → 目標ステアrpm(min/maxクランプ+加速度制限)
  → モード座標PI x2(操舵=共通モード、駆動=差動モード、rpmは一次LPF後)
    → i1 = iSteer + iDrive, i2 = iSteer - iDrive(±current_limitクランプ)
```

- **摩擦フィードフォワードは廃止。** ブレークアウェイ電流は角度・方向依存で
  150〜950mA(2026-07-05電流ランプ実測)とばらつき、固定値FFは過大/過小どちらにも
  なって振動の原因になった。摩擦は定常外乱としてPI積分だけで吸収する。
  そのために `current_limit`(2000)は最悪ブレークアウェイの約2倍の余裕を持たせる。
- **最低ステア速度フロア(`steer_min_rpm`)。** 指令速度がステア約1rpm以下だと
  スティックスリップのリミットサイクルに入る。デッドバンド外では指令の大きさを
  最低2rpmに底上げし、デッドバンド内で0にする。終端接近を連続運動のまま行うのが目的。
- 個別モーターPI+瞬時rpm閾値キック方式は廃止済み(ノイズで左右非同期になり振動)。

## RoboMaster系オープン実装との比較と取り込み(2026-07-06)

DJI公式Development Board C例や大学チームのstandard_robot系に共通するM3508カスケード制御
(角度PID→速度PID→C620電流指令、1kHz)と本実装を比較した。構造(カスケード、速度PI、
摩擦FFなし、1kHz)は既に同等。以下の3点が本実装に無かったため導入した。

1. **積分項の独立クランプ(`mode_integral_limit`、RM系のmax_iout相当)。**
   従来は出力±current_limitに達したときだけ積分を止める条件付きアンチワインドアップで、
   固着中に積分が±2000まで成長できた。ブレークアウェイ実測最大950に対し、動き出しの
   瞬間に積分が過大トルクとして解放されるのがスティックスリップ階段・Ki=200発振の
   一因。クランプ値1200(最悪ブレークアウェイ950より上=静止摩擦には勝てる、
   current_limit=2000より下=解放時の跳びを制限)。
2. **合成電流飽和時のモード比例スケーリング+条件付き積分凍結。**
   従来はm1/m2を個別クランプしており、片側だけ飽和すると操舵/駆動トルク比が暗黙に
   歪む(操舵中の駆動が勝手に増減する交差干渉)。RM系の電力制限が全モーターを比例
   縮小するのと同様に、|iSteer|+|iDrive|>limitのとき両モード電流を共通係数で縮小し、
   トルク方向を保存する。飽和した次周期は両積分を凍結(条件付き積分)。
   ログ用に`torque_scaling_active`を出力へ追加。
3. **駆動(ホイール)目標のランプ(`wheel_accel_rpm_per_s`)。**
   ステア側と違い駆動目標はステップのままPIへ入っていた。実走テスト前に必要。
   初期値200rpm/s(未実測。駆動実走テストで調整すること)。

RM系にあるが採用しなかったもの: 速度ループKd(RM系でも実質0)、積分分離
(本実装は目標がランプで入るため誤差が大きく開かない)、目標角へのフィードフォワード
(steer_min_rpmフロアで代替済み)。

**単位の注意**: 本実装で「mA」と呼んでいる電流値はC620の生指令値(±16384=±20A)。
1カウント≈1.22mAなので、limit=2000は実際には約2.44A。内部的には一貫しているため
改名はしないが、実電流と比較するときは換算すること。

手回し点検待ちとした。2026-07-06、ユーザーによる手回し点検で異常なしを確認し、
再開。イテレーション5で積分クランプ込みの再現に成功。

## 駆動モード(wheel≠0)ステップ応答テスト(2026-07-06)

操舵を起動角に保持したまま、wheel目標を0→50rpmへステップ指令(`wheel_accel_rpm_per_s`=200で
ランプ)。モード非干渉(純駆動でステアが動かないか)と`wheel_accel_rpm_per_s`/`drive_mode_ki`の
実機挙動を評価する新規テスト(`firmware/src/main.c`を書き換え)。ホイールは接地させず浮かせて実施。

| # | 変更 | 結果 |
|---|---|---|
| 8 | 初版: rpm誤差(ランプ後の瞬時値vs実測)が20rpmを超えたら即STOP | ランプが49rpmに達した時点(約245ms)で実測rpmがほぼ0のままerr=46rpmとなり即STOP。**モーターはほぼ無回転**(m1/m2実測rpm=0、電流もi1=i2=0まで戻る=ごく小電流のみ)。ブレークアウェイ電流(150〜950mA)にまだ届いていない段階での誤判定 |
| 9 | ガードに時間猶予1.5秒(`WHEEL_ERROR_CHECK_GRACE_MS`)を追加 | 猶予期間内に実際にモーターが動く兆候(m1実測56rpm、m2実測-101〜-252rpm)。同時に保持していたはずの操舵角が最大-0.615°ドリフト(モード間の機械的カップリングの可能性、非干渉性の検証項目として記録)。ただし`measured_wheel_rpm`の算出値が単発で300〜500rpm相当まで跳ね上がった直後にSTOP。**当初「フィードバックのノイズ/バグ」と誤診断したが、イテレーション10で否定(下記)** |

イテレーション9の直後、ユーザーから「(実機は)全然回ってすらいない」との指摘。イテレーション10の
開ループ試験でC620生フィードバックにはノイズ・異常値が一切出ないことを確認したため、
イテレーション9のスパイクは**フィードバックのノイズやデコードバグではなく、ブレークアウェイ
瞬間の実際の機械的キック(スティックスリップの解放)だった可能性が高い**と訂正する。
発散ガードは「ランプ済み目標との20rpm誤差」を見ていたため、このキック自体(30rpm超の
瞬間的な動き)がガードに引っかかって即STOPしていたと考えられる。

## 駆動(差動)電流のブレークアウェイ確認 — 開ループ(2026-07-06)

イテレーション9のスパイクの原因切り分けのため、PIを完全に排除した開ループ試験を実施。
`motor1=+I, motor2=-I`の純粋な差動電流を500raw/sでランプし、生のC620フィードバック
(motors[N].feedback.rpm/torque_current)をそのまま20ms周期でログした(`firmware/src/main.c`を
書き換え)。ホイールは接地させず浮かせて実施。

| # | 変更 | 結果 |
|---|---|---|
| 10 | 開ループ差動電流ランプ、生rpmを直接ログ | **電流852(raw、上限2000のうち)でm2rpm=-32を検出し正常にブレークアウェイ判定。** それまでm1/m2の生rpmは終始ほぼ0(±3程度のノイズのみ)で、イテレーション9で見た数百rpm相当の異常値は一切再現しなかった。**結論: C620フィードバック自体は健全。ホイールは実際に動く(壊れても固着してもいない)。単に静止摩擦を破るのに約850raw(現状のcurrent_limit=2000の半分弱)が必要で、閉ループ試験(イテレーション8/9)ではPIの積分がそこまで安定して到達する前に発散ガードに引っかかっていた** |

安全のため`CLOSED_LOOP_TEST_ENABLED=0`に戻して書き込み済み。次はこのブレークアウェイ電流
(~850raw、方向依存で変動しうる)を踏まえて、閉ループ側の発散ガード(瞬間的なブレークアウェイ
キックを誤検出しない設計に見直す)と`drive_mode_ki`/`wheel_accel_rpm_per_s`の再チューニングへ。

### イテレーション11: rpm発散ガード撤去、10秒完走(2026-07-06)

current_limitが既にハードクランプしているため、rpm誤差ベースの発散ガードは無駄と判断し撤去
(ユーザー指示)。ガードは角度発散(12°)・センサ/C620タイムアウト・B1・最大試験時間(10秒)のみに
縮小。閉ループのwheelステップテスト(操舵保持+wheel 0→50rpm)を再実行。

結果:
- **誤停止なく10秒間完走**(`STOP: max test duration reached`で正常終了。角度誤差は最大
  でも1.143°、12°のガードには遠く届かず)。
- m1/m2の実測rpmは試験中ずっと非ゼロで振れ続けた(例: 175, -208, 265, -183など)。
  イテレーション10で確認したブレークアウェイ(~850raw)は再現しており、ホイールは
  実際に動いている。
- **ただし滑らかに50rpmへ収束・保持する挙動ではなく、スティックスリップ的な断続動作**。
- **新知見: 保持していたはずの操舵角が、試験開始から終了まで継続的に±0.5〜1.1°の範囲で
  振動し続けた**(単発ドリフトではなく持続的な振動)。角度P制御が常にこの外乱を追いかけて
  `steer_rpm_command`が±2rpm(2000)の間を往復し続けている。差動機構の駆動→操舵への
  機械的カップリングが、想定より強く持続的であることを示す実測データ。
  `CENTRAL_COORDINATED_CONTROL.md`の非干渉性検証項目1の裏付けデータとして重要。

次: (1) この持続的な操舵振動の対策(カップリング補正項、またはangle_deadbandを広げて
振動域を許容するなど)。(2) スティックスリップを抑えて滑らかな50rpm定常回転に近づける
`drive_mode_ki`/`wheel_accel_rpm_per_s`のチューニング。

## 電流ランプ特性化の実測(参考)

開ループで50mA/100msずつ増加、動き出し電流を記録(4試行、開始角度は毎回異なる):

- steer+: 500〜950 / steer-: 450〜950 / drive+: 400〜950 / drive-: 150〜950 mA
- 角度依存が大きい(局所的に硬い箇所がある)。単一のFF定数が成立しない根拠。
- drive方向の検出はC620 rpmノイズ(静止でも±50rpm瞬時)の影響を受けるため参考値。

```c
.motor_max_rpm = 469, .steer_max_rpm = 5, .steer_min_rpm = 2,
.steer_accel_rpm_per_s = 50, .wheel_accel_rpm_per_s = 200 /* 未実測 */,
.angle_kp_rpm_per_deg = 0.5, .angle_deadband_deg = 0.5,
.steer_mode_kp = 5, .steer_mode_ki = 125,   // 150は125より悪化、200は発振NG
.drive_mode_kp = 5, .drive_mode_ki = 100,   // wheel!=0未実施のため125への追随は未検証
.mode_integral_limit = 1200 /* 2026-07-06実機再現確認済み(イテレーション5) */,
.mode_rpm_filter_tau_s = 0.02, .current_limit = 2000, .steer_motor_sign = 1,
```

ベスト実績更新(2026-07-06、イテレーション6、steer_mode_ki=125): +10°ステップを約3.0秒、
終端誤差0.02°、1サンプルのみ-0.107°の軽微なオーバーシュート。イテレーション7でKi=150を
試したが3.25秒/0.332°まで悪化したため125を確定値とする。`drive_mode_ki`は同時に上げていない
(wheel=0のステアのみの試験のため未検証)。駆動実走試験を行う際に個別調整すること。

注意: `mode_integral_limit`(=1200)は2026-07-06のイテレーション5で積分クランプ込みの
実機再現に成功済み(挙動差なし)。

## テスト運用の注意

- テストアプリは起動時に1回だけ自動開始(目標=起動角+10°)。B1で中断ラッチ。
  固定タイムアウトは廃止(停止条件: B1・センサ異常・C620途絶・誤差12°超)。
- **ST-LINK VCPは未読データをバッファし、モニタ接続時に古いログを再生する。**
  新しい試験の `START:` 行(target=起動角+10°)より前の行は解析に使わない。
  これを見誤り「リセット後も発振継続」と誤診した事例あり。
- 調整の反復手順は `.claude/skills/gain-tuning/SKILL.md`(gain-tunerエージェント用
  ランブック)に固めてある。

## 安全状態

`src/main.c` の `CLOSED_LOOP_TEST_ENABLED` は既定0(B1を押しても電流0)。
監督付き試験時のみ1にする。現在は0で引き渡し済み。
